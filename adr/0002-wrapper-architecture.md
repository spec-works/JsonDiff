# ADR 0002: Wrapper Architecture with Temporary External Library

## Status

Accepted

## Context

SpecWorks is in Phase 1: Proof of Concept. The goal is to demonstrate that the software factory pattern works by generating specification-compliant components. However, generating every component from scratch immediately would delay proving the concept.

For JSON Patch (RFC 6902) functionality, there are two main approaches:

### Option 1: Generate Full Implementation Immediately
- Implement RFC 6902 diff generation from scratch
- Write comprehensive test suite
- Validate against RFC compliance
- Time investment: significant upfront cost
- Delays proving other aspects of SpecWorks

### Option 2: Use Existing Library Directly
- Depend on SystemTextJson.JsonDiffPatch
- Expose their API directly in SpecWorks components
- Fast to implement
- **Critical Problem**: Exposes non-RFC 6902 features (other formats, proprietary options)
- Creates tight coupling to external API
- Difficult to migrate later

### Option 3: Thin Wrapper Around External Library
- Create SpecWorks interface defining desired API
- Implement adapter using external library internally
- Constrain API to RFC 6902 only (per ADR 0001)
- Enables future migration to native implementation

## Decision

Implement a **thin wrapper architecture** that:

1. **Defines SpecWorks interface**
   - `IJsonDiffGenerator` with RFC 6902-only methods
   - Uses standard .NET types (`JsonPatchDocument`, `JsonNode`)
   - No exposure of external library types

2. **Uses SystemTextJson.JsonDiffPatch temporarily**
   - Implement via adapter pattern
   - Hide all non-RFC 6902 features
   - Keep as internal implementation detail

3. **Enables future migration**
   - When SpecWorks generates its own RFC 6902 component, swap the adapter
   - Consumer code unchanged
   - Seamless transition

## Implementation Guidelines

### Package Structure

```
SpecWorks.JsonDiff/
├── src/
│   ├── IJsonDiffGenerator.cs           // Public interface
│   ├── JsonDiffGenerator.cs            // Public factory/facade
│   └── Adapters/
│       └── SystemTextJsonAdapter.cs    // Internal adapter (v1.x only)
├── specs.json                          // RFC 6902 linkset
└── README.md                           // Documents temporary nature
```

### Public API

```csharp
namespace SpecWorks.JsonDiff
{
    // Public interface - stable, version-agnostic
    public interface IJsonDiffGenerator
    {
        JsonPatchDocument CreateDiff(JsonNode source, JsonNode target);
    }

    // Public factory - hides implementation choice
    public class JsonDiffGenerator : IJsonDiffGenerator
    {
        private readonly IJsonDiffGenerator _implementation;

        public JsonDiffGenerator()
        {
            // v1.x: Use adapter
            _implementation = new SystemTextJsonAdapter();

            // v2.x: Use native implementation
            // _implementation = new JsonDiffGeneratorImpl();
        }

        public JsonPatchDocument CreateDiff(JsonNode source, JsonNode target)
            => _implementation.CreateDiff(source, target);
    }
}
```

## Consequences

### Positive

1. **Fast time-to-market**: Can deliver working component quickly
2. **Interface stability**: Public API won't change during migration
3. **Format enforcement**: Wrapper constrains to RFC 6902 only
4. **Proof of concept**: Enables other SpecWorks work to proceed
5. **Migration path**: Clear strategy for moving to native implementation
6. **Dependency isolation**: External library hidden from consumers
7. **Testing clarity**: Can test interface separate from implementation

### Negative

1. **External dependency**: Still depends on SystemTextJson.JsonDiffPatch temporarily
2. **Wrapper maintenance**: Small amount of adapter code to maintain
3. **Performance overhead**: Extra method call (negligible in practice)
4. **Version coordination**: Must ensure adapter stays compatible
5. **Documentation burden**: Must explain temporary nature

### Mitigation

- **README disclaimer**: Clearly state v1.x uses external library, v2.x will use native implementation
- **Semantic versioning**: v1.x = adapter, v2.x = native (breaking change for dependencies only)
- **Internal marking**: Adapter is `internal`, consumers never reference it
- **Interface first**: All tests written against `IJsonDiffGenerator`, not adapter

## Migration Strategy

### Version 1.x (Current - POC Phase)
```xml
<PackageReference Include="SystemTextJson.JsonDiffPatch" Version="2.0.0" />
```
- Use adapter pattern
- README states: "Current implementation uses SystemTextJson.JsonDiffPatch"

### Version 2.0 (Future - After SpecWorks Factory Proves Out)
```xml
<!-- No external dependencies -->
```
- Remove SystemTextJson.JsonDiffPatch dependency
- Implement `JsonDiffGeneratorImpl` using SpecWorks-generated code
- Update README: "Native RFC 6902 implementation"
- **Consumer code unchanged** - still uses `IJsonDiffGenerator`

## Examples

### Consumer Code (Stable Across Versions)

```csharp
using SpecWorks.JsonDiff;
using System.Text.Json.Nodes;

// This code works in both v1.x and v2.x
var generator = new JsonDiffGenerator();
var patch = generator.CreateDiff(source, target);

// Consumer never knows about adapter vs native implementation
```

### README Statement

```markdown
## Implementation Note

**Version 1.x** (Current): This component uses SystemTextJson.JsonDiffPatch
as the underlying implementation. The public API (`IJsonDiffGenerator`)
abstracts this dependency.

**Version 2.x** (Future): Will use a native SpecWorks-generated RFC 6902
implementation. Consumer code will not require changes.

This approach allows SpecWorks to deliver working components during the
Proof of Concept phase while maintaining the vision of fully generated
specification-compliant components.
```
